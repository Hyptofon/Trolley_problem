# Проблема вагонетки (The Trolley Problem) — Vercel & Upstash Redis

Інтерактивний, високопродуктивний та доступний вебсайт для дослідження класичної морально-етичної дилеми «Проблема вагонетки» з анонімним навчальним голосуванням, візуальною SVG-анімацією, атомарним збереженням голосів у **Upstash Redis** через Redis Lua `EVAL`, серверними Route Handlers на **Next.js App Router (Vercel Functions)** та криптографічно захищеною адмінпанеллю організатора.

## 1. Концепція та дилема

Проєкт реалізує **одну класичну ситуацію** мисленнєвого експерименту Філіппи Фут (1967):
- Некерована вагонетка мчить колією в напрямку **п'ятьох людей**, які не можуть зійти з рейок самостійно.
- Учасник стоїть біля стрілочного переводу та має **рівно два рішення**:
  1. `stay` — **«Не втручатися»**: вагонетка продовжує рух прямо, під прямою загрозою 5 людей. Фізичної дії не відбувається.
  2. `switch` — **«Перевести стрілку»**: стрілка перемикається, вагонетка повертає на бокову колію, де під загрозою опиняється 1 людина (рятуються 5).

> [!NOTE]
> У проєкті **немає** жодних сторонніх сценаріїв, моральних повчань, збору персональних даних (імен, email, телефонів, геолокації), реєстрації відвідувачів чи суб'єктивної оцінки «правильності» вибору. Загальні результати голосування учасникам за замовчуванням не показуються, щоб не впливати на їхнє власне рішення.

## 2. Архітектура та потік даних

Єдиний репозиторій Next.js, який розгортається на Vercel (Hobby) із зовнішнім безкоштовним хмарним сховищем Upstash Redis (Free):

```text
Відвідувач (анонімний, без авторизації)
  │
  ├── GET /                                (Next.js App Router UI)
  │     ├── POST /api/vote/status          (перевірка: чи голосував цей браузер?)
  │     └── POST /api/vote                 (відправлення рішення: stay або switch)
  │           │
  │           └── Server-side VoteService
  │                 └── Upstash Redis EVAL Lua (Атомарна перевірка дубля + лічильник HINCRBY)
  │
Організатор (Адміністратор)
  │
  └── GET /admin                           (форма входу, статистика прихована)
        │
        ├── POST /api/admin/login          (перевірка пароля scrypt; Redis-сесія 8h + HttpOnly cookie)
        ├── GET  /api/admin/session        (перевірка активності сесії)
        ├── POST /api/admin/logout         (інвалідація сесії в Redis та видалення cookie)
        │
        └── GET  /api/admin/stats          (доступ ТІЛЬКИ після валідації сесії, Cache-Control: no-store)
               │
               └── Upstash Redis HGETALL   (читання агрегатів stay/switch/updatedAt)
```

### Ключові архітектурні гарантії:
1. **Атомарний запис через Redis Lua EVAL:**  
   Усі операції перевірки наявності голосу та інкременту лічильника виконуються в єдиному Redis Lua скрипті (`ATOMIC_VOTE_LUA`). Навіть при 25+ одночасних конкурентних запитах з одного браузера зараховується рівно один голос, а лічильник збільшується рівно на 1. При повторній спробі проголосувати повертається статус `already_voted` і **початковий** вибір без зміни статистики.
2. **Анонімність без збереження UUID у Redis:**  
   Клієнтський браузерний UUID хешується на сервері через HMAC-SHA256 із секретом `VOTE_ID_HMAC_SECRET`. У Redis зберігається лише дайджест `voter:{digest}`, а сирий UUID ніколи не записується в базу та логи.
3. **Захист адмінпанелі:**  
   - Пароль адміністратора зберігається виключно у вигляді salted `scrypt` хешу (`ADMIN_PASSWORD_HASH`).
   - Перевірка виконується за допомогою `crypto.timingSafeEqual` для захисту від timing attacks.
   - Токен сесії (32 байти криптографічної ентропії) зберігається в `HttpOnly`, `SameSite=Strict`, `Secure` cookie. У Redis зберігається лише SHA-256 хеш токена з TTL 8 годин.
   - Захист від перебору паролів (Rate Limiting) на рівні Redis (5 спроб на хвилину).
   - Захист від CSRF: обов'язкова валідація заголовка `Origin`/`Referer` для всіх мутуючих запитів.
4. **Fail-Closed принцип:**  
   У продакшені за відсутності або недоступності Upstash Redis API повертає контрольовану помилку `503 STORAGE_ERROR`, не створюючи помилкових підтверджень збереження голосу.

## 3. Схема ключів Redis

- `trolley:{environment}:v1:voter:{idDigest}` — рядок `stay` або `switch` (без TTL на час експерименту).
- `trolley:{environment}:v1:counts` — Redis Hash з полями `stay`, `switch`, `updatedAt`. Загальна кількість обчислюється як сума `stay + switch`.
- `trolley:{environment}:v1:admin-session:{sessionHash}` — маркер сесії з TTL 28800 сек (8 годин).
- `trolley:{environment}:v1:ratelimit:{action}:{ip}` — лічильник спроб із короткоживучим TTL.

## 4. Швидкий старт локально

### 4.1. Встановлення залежностей
```bash
npm install
```

### 4.2. Налаштування середовища розробки
Створіть файл `.env.local` на основі `.env.example`:
```bash
cp .env.example .env.local
```

Для локальної розробки інтерфейсу без підключення до реального Redis увімкнено демонстраційний режим (`DEMO_MODE=true`), який використовує швидкий in-memory адаптер із плашкою «Демо: голоси не зберігаються».

Щоб згенерувати власний пароль адміністратора для тестування:
```bash
npm run generate-hash "МійНадійнийПароль123"
```
Скопіюйте згенерований `ADMIN_PASSWORD_HASH` у `.env.local`.

### 4.3. Запуск локального сервера
```bash
npm run dev
```
Відкрийте `http://localhost:3000` у браузері.  
Адмінпанель доступна за адресою `http://localhost:3000/admin`.

## 5. Розгортання на Vercel (Hobby) + Upstash Redis (Free)

Розгортання здійснюється у безкоштовних межах тарифів **Vercel Hobby** та **Upstash Redis Free**:

### Крок 1. Підготовка репозиторію
1. Створіть репозиторій на GitHub та запуште гілку `feat/trolley-vercel-upstash` (або `main`).
2. Переконайтеся, що файл `.env.local` додано до `.gitignore` і він не потрапляє у Git.

### Крок 2. Імпорт проєкту у Vercel
1. Увійдіть на [vercel.com](https://vercel.com).
2. Натисніть **Add New...** → **Project**.
3. Оберіть ваш репозиторій на GitHub та натисніть **Import**.
4. Фреймворк автоматично розпізнається як **Next.js**.

### Крок 3. Підключення безкоштовного Upstash Redis через Vercel Marketplace
1. У панелі проєкту Vercel перейдіть у вкладку **Storage** або **Marketplace**.
2. Знайдіть **Upstash for Redis** та натисніть **Install / Create**.
3. Оберіть **Free** план (256 МБ сховища, 500 000 команд/місяць, $0/міс).
4. Підключіть створену базу даних до вашого проєкту. Vercel автоматично додасть змінні середовища `UPSTASH_REDIS_REST_URL` та `UPSTASH_REDIS_REST_TOKEN` (або `KV_REST_API_*`).

### Крок 4. Налаштування секретів у Vercel Project Settings
Перейдіть у **Settings** → **Environment Variables** вашого проєкту на Vercel і додайте:
- `ADMIN_PASSWORD_HASH`: згенерований salted scrypt рядок (отримайте локально командою `npm run generate-hash "ВашСкладнийПароль"`).
- `VOTE_ID_HMAC_SECRET`: криптографічний ключ щонайменше 32 символи (згенерований, наприклад, через `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`).
- `REDIS_KEY_PREFIX`: `trolley:production:v1` (для продакшену).
- `DEMO_MODE`: `false`.

### Крок 5. Деплой та Smoke Test
1. Натисніть **Deploy** (або запустіть **Redeploy** після встановлення змінних середовища).
2. Отримайте робоче посилання виду `https://<project-name>.vercel.app`.
3. **Smoke Test:**
   - Відкрийте головну сторінку та оберіть рішення.
   - Перевірте, що голос зафіксовано, а анімація відобразила обраний наслідок.
   - Оновіть сторінку — має відновитися ваш вибір без можливості повторного голосування.
   - Перейдіть на `/admin`, виконайте вхід за встановленим паролем.
   - Перевірте коректність відображення лічильників, відсотків та графіка.
   - Перевірте презентаційний режим (кнопка «Презентаційний режим»).
   - Натисніть «Вийти» та переконайтеся, що доступ до `/api/admin/stats` блокується з кодом 401.

### Крок 6. Перевірка даних в Upstash Console
Організатор може в будь-який час зайти в [Upstash Console](https://console.upstash.com) → обрати базу даних → **Data Browser**:
- У ключі `trolley:production:v1:counts` зберігаються фінальні агрегати (`stay`, `switch`, `updatedAt`).
- Значення лічильників можна зафіксувати або скопіювати після завершення навчального заходу.

Проєкт містить повне багаторівневе покриття тестами без використання фальшивих заглушок:

```bash
# 1. Перевірка статичних типів TypeScript у суворому режимі (strict)

# 2. Перевірка стилю коду та правил Next.js Core Web Vitals

# 3. Модульні та інтеграційні тести (Vitest, 90 тестів, 12 тест-сьютів)
npm run test

# 4. Перевірка покриття коду (>85% statements/functions, 100% shared/validation)
npm run test:coverage

# 5. Наскрізні E2E тести (Playwright, 14 тестів: Desktop Chromium + Pixel 5 Mobile)
npm run test:e2e

# 6. Оптимізована production збірка Next.js App Router
npm run build

# 7. Комплексна верифікація всіх Quality Gates однією командою:
npm run verify
```

### Склад тестових наборів:
- **Unit (`tests/unit/`):**
  - `statsCalculator.test.ts`: обчислення відсотків при 0/0, 1/0, 0/1, дробових частках, великих числах та некоректних даних.
  - `participant.test.ts`: генерація, валідація UUID v4, збереження у `localStorage`.
  - `validation.test.ts`: Zod-схеми запитів голосування, статусу та входу адміністратора.
  - `crypto.test.ts`: детермінований HMAC-SHA256, salted scrypt хешування, захист від timing attacks, безпечні токени сесій.
  - `cookiesAndCsrf.test.ts`: HttpOnly/SameSite/Secure cookies, захист від CSRF по Origin/Referer.
  - `apiService.test.ts`: клієнтська обробка тайм-аутів, мережевих помилок, статусів відповідей.
- **Backend & Atomicity (`tests/backend/`):**
  - `voteRoutes.test.ts`: перевірка HTTP статусів 200, 400, 403, 405, 413, 415, 429 для `/api/vote` та `/api/vote/status`.
  - `redisAtomicity.test.ts`: стрес-тест **25 одночасних паралельних запитів** з одного браузера (рівно 1 recorded, 24 already_voted; лічильник збільшено строго на 1), 30 паралельних запитів від різних учасників (точна сума), незмінність першого вибору.
  - `adminRoutes.test.ts`: життєвий цикл сесії, блокування неавторизованого доступу (401), rate limiting, відкликання токена при logout.
- **Frontend Integration (`tests/frontend/`):**
  - `HomePage.test.tsx`: рендер двох рішень, блокування подвійного кліку, відновлення статусу при релоаді, обробка помилок зв'язку та повторна спроба.
  - `AdminPage.test.tsx`: прихованість даних до авторизації, вхід, оновлення, порожній стан (0 голосів), презентаційний режим, вихід.
  - `App.test.tsx`: рендер шапки, підвалу та сторінки 404.
- **End-to-End (`tests/e2e/`):**
  - `voting.spec.ts`: наскрізні сценарії голосування desktop + mobile.
  - `admin.spec.ts`: авторизація, статистика, перемикання презентаційного режиму.
  - `accessibility.spec.ts`: автоматизований аудит доступності через `@axe-core/playwright` (WCAG 2.2 AA).

## 7. Доступність (WCAG 2.2 AA)

- **Контрастність:** графітова темна палітра (`bg-graphite-950`, контрастність тексту > 7:1).
- **Кольоронезалежність:** рішення диференціюються текстом, позицією та іконками, а не лише кольором.
- **Клавіатурне керування:** повна підтримка `Tab`, `Enter`, `Space` із видимим індикатором фокусу `focus-visible`.
- **Скрінрідери:** семантичний HTML5, текстова альтернатива для SVG-сцени, `aria-live` оповіщення для зміни станів.
- **`prefers-reduced-motion`:** автоматичне вимкнення анімації для користувачів із чутливістю до руху; наявність кнопки «Пропустити анімацію».
- **Етичність візуалізації:** повна відсутність графічного насильства, крові чи травм.
